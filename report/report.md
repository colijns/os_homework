## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本次实验在实验一的基础上完成物理内存管理，并建立一个最简单的页表映射。首先发现系统中的物理内存，接着建立对物理内存的初步管理，最后对页表进行相关操作，实现虚拟内存到物理内存之间的映射。

```text
DTB 提供物理内存范围
          ↓
page_init() 建立 Page[]，排除保留区域
          ↓
init_memmap() 将完整空闲页交给 pmm_manager
          ↓
pmm_manager：First-Fit / Best-Fit / Buddy System（三种可选策略）
          ↓
alloc_pages() / free_pages()：分配与回收连续物理页
          ↓
SLUB：利用物理页提供 kmalloc() / kfree()（扩展任务）
```

虚拟地址转换是本章的另一条主线：启动汇编设置 `satp`，启用预设 Sv39 页表；访存时先查询 TLB，未命中时再遍历页表。

### 3.2 核心调用顺序

内核启动时的实际调用顺序为：

```text
entry.S：保存 DTB 地址，设置 satp
          ↓
kern_init()
    ├─ dtb_init()：读取设备树中的内存信息
    ├─ pmm_init()
    │    ├─ init_pmm_manager()：选择一种页分配策略
    │    ├─ page_init() → init_memmap()：登记空闲页
    │    └─ check_alloc_page()：检查页分配器
    ├─ slub_init()：初始化对象分配器
    └─ slub_check()：检查对象分配并复查底层页分配器
```

## 4.1 功能模块一：物理内存初始化功能

### 4.1.1 任务一：实现物理内存探测与页描述符初始化功能

**负责人：** 2411276-林靖然

#### 模块功能描述

**需要实现/修改的函数：**

```c
static void page_init(void);  // kern/mm/pmm.c
```

**功能说明：**

`dtb_init()` 先从设备树读取内存范围，`page_init()` 再通过 `get_memory_base()` 和 `get_memory_size()` 取得该范围。函数检查物理内存起点、大小和终点溢出，并把可管理上界限制在 `PHYSICAL_MEMORY_END` 内、向下按页对齐；无效范围直接 `panic()`。

接着设置虚实地址偏移 `va_pa_offset` 和物理页上界 `npage`。`pages` 放在链接符号 `end` 之后的页边界，每个 `Page` 描述一个从 `DRAM_BASE` 开始的物理页；`pages` 本身是虚拟地址，计算描述符数组占用空间时必须先用 `PADDR(pages)` 得到物理地址。初始化时先将所有页面标为保留，再从描述符数组末尾向上对齐，确定首个完整空闲页 `free_pa`。最后调用：

```c
init_memmap(pages + (PPN(free_pa) - nbase),
            (maxpa - free_pa) / PGSIZE);
```

这样，OpenSBI、内核镜像和 `Page[]` 占用的页面不会进入空闲区；若描述符数组放不下，或已没有完整空闲页，则通过 `panic()` 终止初始化。

#### 需求规格与提示词

本任务的 **Pre-Condition** 是 `dtb_init()` 已提供内存信息，且 `pmm_manager` 已初始化。**Post-Condition** 是成功时设置 `va_pa_offset`、`npage`、`pages`，并将完整空闲页交给当前管理器。规格还明确了三类异常：DTB 范围无效、描述符数组越界、没有完整空闲页；这些情况均不能把错误页面登记为可分配页。

#### 最终提示词

本任务采用 `[PROMPT]—[RELY]—[GUARANTEE]—[SPECIFICATION]` 四段式。`PROMPT` 限定只修改 `page_init()`；`RELY` 列出 DTB、内存布局、`Page` 和地址转换接口；`GUARANTEE` 固定函数签名并禁止修改测试；`SPECIFICATION` 写明有效范围、保留区和异常处理。提示词中特别强调：`end` 与 `pages` 是虚拟地址，`PPN` 是物理页号，`init_memmap()` 的参数分别是 `Page *` 和页数。最终提示词原文见 [prompt.md](./prompt.md) 。

### 4.1.2 扩展任务 Challenge：硬件的可用物理内存范围的获取方法

**负责人：** 2411276-林靖然

如果内核事先不知道物理内存的范围，可以让固件或引导程序在启动时提供内存布局。内核不能随意读写物理地址来探测内存，因为有些地址对应外设，还有些地址根本没有映射。

在本实验中，QEMU 生成设备树，OpenSBI 把设备树地址通过寄存器 `a1` 传给内核。`entry.S` 保存这个地址，`dtb_init()` 再从设备树 `memory` 节点的 `reg` 属性读取内存起点和大小。得到这段范围后，`page_init()` 还要避开 OpenSBI、内核镜像和 `Page` 数组占用的页面，只把剩余的完整页面加入空闲区。这些处理完成后，内核得到的才是可以交给页面分配器的物理页范围。

## 4.2 功能模块二：物理内存分配功能

### 4.2.1 任务一：理解 First-Fit 连续物理内存分配算法

**负责人：** 2411294-王烨

First-Fit 使用按地址递增排列的空闲块链表，每个空闲块的首页通过 `property` 保存页数，并用 `PageProperty` 标识块头。结合 `kern/mm/default_pmm.c`，主要函数的作用如下：

| 函数 | 核心行为 |
| --- | --- |
| `default_init()` | 初始化空闲链表，将空闲页总数设为零。 |
| `default_init_memmap(base, n)` | 检查页面原来处于保留状态，清理描述符并设置引用计数；将这段内存登记为一个空闲块，按地址插入链表，累计空闲页数。 |
| `default_alloc_pages(n)` | 从链首查找第一个至少有 `n` 页的块；取出前 `n` 页，把剩余部分作为新空闲块留在原位置，减少空闲页总数。没有足够大的连续块时返回 `NULL`。 |
| `default_free_pages(base, n)` | 恢复待释放页的状态，按地址插回链表；先检查前驱，再检查后继，地址相邻时合并块并清理旧块头，恢复空闲页计数。 |

First-Fit 不需要找出全局最优块，找到首个可用块即可停止，最坏查找时间仍为 O(m)，其中 m 是空闲块数。它可能反复切割低地址区域，留下许多小块；即使空闲页总数足够，也可能因缺少连续块而分配失败。可通过分级空闲链表减少扫描，或采用 Next-Fit 从上次位置继续查找，但这些策略也会改变碎片分布，不能保证对所有请求序列都更优。

### 4.2.2 任务二：实现 Best-Fit 连续物理内存分配算法
**负责人：** 2411294-王烨

Best-fit 算法与 First-fit 算法的唯一区别在于页面分配。First-fit 算法将空闲分区链以地址递增的顺序连接，在进行内存分配时，从链首开始顺序查找，直到找到一块分区的大小可以满足需求时，按照该作业的大小，从该分区中分配出内存，将剩下的空闲分区仍然链在空闲分区链中。而 Best-fit 算法的目标是在所有可满足请求的空闲块中选出最小的一块，使切割后产生的剩余碎片尽量小，从而尽量保住大块。

需要说明的是，本实现并没有把链表真正按大小排序，而是沿用 First-Fit 的地址有序链表，在分配时遍历整条链表选出最小可满足块，效果等价于按大小取最优，且释放时可复用同一套"按地址插入 + 相邻合并"的逻辑。

**需要实现/修改的函数：**
````c
static void best_fit_init(void); // 与 default 相同
static void best_fit_init_memmap(struct Page *base, size_t n); // 与 default 相同
static struct Page *best_fit_alloc_pages(size_t n); // 核心差异：全表扫描取最小合适块
static void best_fit_free_pages(struct Page *base, size_t n); // 与 default 相同
````

并在 `best_fit_pmm_manager` 中绑定上述六个成员函数。

由于与 First-Fit（`default_pmm.c`）相比，只有 `alloc_pages` 的查找策略不同，其余函数保持一致，该部分没有借助AI实现，完全使用人工编写。

对于`alloc_pages`的核心实现如下：
````c
struct Page *page = NULL;
size_t minsize = nr_free + 1; // 空闲块不可能大于空闲页总数
while ((le = list_next(le)) != &free_list) { // 遍历整条链表
    struct Page *p = le2page(le, page_link);
    if ((p->property >= n) && (p->property < minsize))
    {
    page = p; // 记录当前最优块
    minsize = p->property;
    }
}
````

#### 算法可改进的部分
事实上，First-Fit 平均只需扫描链表前半段，而 Best-Fit 的最坏情况和平均情况都是 O(m)。当系统长时间运行、空闲链被切割得越来越碎时，m 增长会直接拖慢每一次分配。工程上可考虑三种典型改进：

1. **平衡树索引**：把空闲块按 `(size, addr)` 作为关键字插入红黑树，分配时查 `lower_bound(n)` 即得最小可满足块，复杂度降为 O(log m)；同时仍保留一条按地址有序的双向链表用于 O(1) 相邻合并。
2. **最小堆 / 优先队列**：以块大小为堆键，分配取堆顶后再检查是否 ≥ n，不足则弹出继续取；释放时插入堆。
3. **分级空闲链表**：按块大小划分若干档（如 1、2、4…2^k 或对数分桶），每档一条链表；分配先在最小非空档内找，找不到再向上一档。
### 4.2.3 任务三：Buddy System（伙伴系统）分配算法
**负责人：** 2411294-王烨

伙伴系统把空闲内存组织成大小为 `2^order`页的块，并按阶（order）分类管理：任何大小为 2^k 页、起始页号按 2^k 对齐的块，其"伙伴"是同阶、页号仅在第 k 位上相反的块（`pfn XOR 2^k`）。分配时自满足需求的最低阶向上找块、再逐级对半分裂；释放时反复与伙伴合并，直到不能合并为止。这一结构以 O(log n) 的代价换取了分裂与合并的快速进行。

#### 模块功能描述

伙伴系统把物理页按 `2^order` 分级管理：第 `order` 级空闲链表中的每个空闲块包含 `2^order` 个连续物理页。空闲块只由“块头页”标识：块头 `PG_property=1` 且 `property=2^order`，块内其余页的 `flags/property` 必须为 0。分配时把请求页数向上取整到不小于 `n` 的最小 `2^k`，从第 `k` 级开始向上找到第一个非空链表，摘取大块后逐级二分，右半块挂回低一级链表，左半块继续用于分裂，最终返回左半块首页。释放时按同样规则向上取整，利用物理页号计算伙伴：

```c
buddy_pfn = pfn ^ (1 << order);
```

若伙伴是同一阶的空闲块头，则摘下伙伴并与当前块合并，块头取地址较低者，继续向更高阶合并；否则停止合并并将最终块挂入对应级链表。

**需要实现/修改的函数：**

```c
static void buddy_init(void);
static void buddy_init_memmap(struct Page *base, size_t n);
static struct Page *buddy_alloc_pages(size_t n);
static void buddy_free_pages(struct Page *base, size_t n);
static size_t buddy_nr_free_pages(void);
static void buddy_check(void);
```

并在 `buddy_fit_pmm_manager` 中绑定上述六个成员函数。

#### 需求规格与提示词

本任务采用 `[PROMPT]—[RELY]—[GUARANTEE]—[SPECIFICATION]` 四段式提示词辅助完善 `kern/mm/buddy_fit_pmm.c`。其中
`buddy_fit_pmm.h`和`buddy_fit_pmm.c`中部分初始化函数为人工实现，提示词只针对伙伴系统分配算法本身。

**Pre-Condition：**

- `buddy_init()` 已初始化 `free_area[0..BUDDY_MAX_ORDER-1]` 与全局 `nr_free`；
- `buddy_init_memmap()` 收到的页均为 `PageReserved`；
- `alloc_pages/free_pages` 的 `n > 0`；
- `free_pages` 释放的页不能是保留页，也不能已经是空闲块头，防止重复释放。

**Post-Condition：**

- `buddy_init_memmap(base, n)` 按物理页号自然对齐，把 `[base, base+n)` 贪心切分为若干 `2^order` 块并挂入对应级链表，`nr_free` 累计为 `n`；

#### check 测试覆盖的核心行为与边界情况

`buddy_check()` 以 `nr_free_store` 保存初始空闲页数，并在每类操作后要求 `nr_free == nr_free_store`，测试逻辑全部收在 `buddy_fit_pmm.c` 内部，通过 `.check` 成员触发。它覆盖了以下核心行为和边界情况：

- **最小请求与基本分配/释放**：连续分配三个单页 `p0、p1、p2`，断言三者非空且互不相同、引用计数为 0、`page2pa(p0) < npage * PGSIZE`，随后逐个释放并检查空闲页数恢复。这覆盖了 `order=0` 的最小块分配、释放入链和全局计数行为。
- **非 2 的幂请求的向上取整与块对齐**：`alloc_pages(5)` 应返回一个 `order=3` 的 8 页块；断言 `(page2ppn(p3) & (8 - 1)) == 0` 直接验证 8 页块起始物理页号按 8 页对齐；断言 `!PageProperty(p3)` 验证返回块头已不再是空闲块。随后 `free_pages(p3, 5)` 必须按同样的向上取整规则归还 8 页，并保持 `nr_free` 守恒。这覆盖了非 2 幂请求的取整、分裂、释放取整对称性。
- **大块分裂与伙伴完全合并**：`alloc_pages(64)` 返回 `order=6` 的 64 页块，并断言其物理页号按 64 页对齐；随后分别释放 `p4` 的 32 页和 `p4 + 32` 的 32 页。由于 `p4` 按 64 页对齐，`p4` 与 `p4 + 32` 是 `order=5` 的伙伴，第二次释放应触发逐级合并回 `order=6`，最终 `nr_free` 恢复。这覆盖了伙伴异或定位、同阶空闲块头判断、块头取低地址以及逐级合并。
- **连续多页分配与逆序释放的页数守恒**：连续分配最多 64 个单页到 `stress[]`，要求 64 次全部成功；再按逆序逐个释放，最后要求 `nr_free == nr_free_store`。这覆盖了重复分配/释放、不同来源的空闲块、逆序释放时合并顺序变化，以及不泄漏、不重复计数。
- **边界大小组合**：测试包含 `n=1`、`n=5`（非 2 幂）、`n=32/64`（2 的幂）、连续 64 次单页分配等不同规模，能同时触发小阶分配、大块分裂、释放合并和批量操作路径。

`buddy_check()` 没有显式构造“全局空闲页不足”或“空闲页数足够但没有足够大连续块”的失败分支；这两类分支由 `buddy_alloc_pages()` 中 `n > nr_free` 与向上查找非空链表的逻辑保证，测试通过成功路径和每轮页数守恒间接约束其不会误改状态。

#### 为什么这些测试能够有效检验 Buddy System 实现

- **页数守恒检查能发现取整不对称和计数错误**：每次测试前后比较 `nr_free`，如果 `alloc_pages(5)` 按 8 页分配而 `free_pages(5)` 只归还 5 页，或合并后 `nr_free` 多减/多加，都会立即失败。
- **对齐断言直接验证 Buddy 的核心不变量**：`order=k` 的空闲块起始物理页号必须按 `2^k` 对齐。`(page2ppn(p3) & 7) == 0` 和 `(page2ppn(p4) & 63) == 0` 能发现分裂后返回错误半块、块头选择错误，或用数组下标代替物理页号计算伙伴等问题。
- **块头属性检查验证返回状态正确**：`!PageProperty(p3)` 能发现分配后未清除块头空闲属性、返回块内非头页等错误。
- **两半释放能验证伙伴定位和逐级合并**：分别释放 `p4` 和 `p4 + 32` 后必须完全合并；若伙伴计算未使用 `pfn ^ (1 << order)`、未检查伙伴是否为同阶空闲块头，或合并后未更新块头，页数守恒或后续分配会失败。
- **逆序批量释放能验证重复操作和合并顺序**：连续分配 64 个单页再逆序释放，覆盖多次分裂、入链、合并和计数更新，能发现链表损坏、重复释放、合并遗漏等问题。
### 4.2.4 Challenge：任意大小的内存单元 SLUB 分配算法

**负责人：** 2411795-阎科霖

#### 模块功能与两层结构

本部分在已有物理页分配器上实现按字节申请内核内存的接口。底层仍使用 A、B 完成的 `alloc_pages()/free_pages()`；上层把一页拆成多个对象槽位，使小对象可以共享物理页。当前默认后端仍为 Buddy，SLUB 不改变 `Page` 布局和原有页分配器的实现。

新增实现位于 [`slub.c`](../code/kern/mm/slub.c) 和 [`slub.h`](../code/kern/mm/slub.h)，独立测试位于 [`slub_test.c`](../code/kern/mm/slub_test.c)。`kern/init/init.c` 在 `pmm_init()` 成功后依次调用 `slub_init()` 和 `slub_check()`。

```text
kmalloc(size)
    ├─ 1～2048 字节：选择大小类别 → partial slab → 空闲对象槽位
    └─ 大于 2048 字节：负载 + 16 字节管理头 → 连续物理页

kfree(ptr)
    ├─ 小对象：归还槽位；最后一个在用对象释放后归还整页
    └─ 大对象：读取实际页数，归还同样大小的连续页块
```

#### 需求规格与接口

**Pre-Condition：** `pmm_init()` 已完成物理页初始化与原有自检；在单 hart、非重入的内核启动阶段调用一次 `slub_init()`。释放时，除 `NULL` 外只能传入尚未释放的原始对象指针。

**Post-Condition 与异常行为：**

| 接口 | 规格 |
| --- | --- |
| `void slub_init(void)` | 初始化八个对象缓存，不预先申请 slab 页。 |
| `void *kmalloc(size_t size)` | 成功时返回至少 16 字节对齐、可写入请求长度的内存；同时在用对象的请求区间互不重叠，返回内容不保证清零。 |
| `void kfree(void *ptr)` | 调用者不必提供大小；`kfree(NULL)` 无副作用，其他有效对象按所属类型回收。 |
| 分配失败 | 零长度、整数溢出、过大请求或空间不足返回 `NULL`，不消耗物理页。 |
| 全部释放 | 空 slab 立即交回 PMM；所有对象释放后空闲页数应恢复。 |

#### 核心数据结构与小对象流程

小对象缓存的大小为 16、32、64、128、256、512、1024、2048 字节，请求选择能容纳它的最小类别。例如 `kmalloc(23)` 使用 32 字节槽位，剩余 9 字节属于内部碎片。

`slub_cache` 保存对象大小和 partial 链表；每个 slab 使用一页，页内的 `slub_slab` 记录所属缓存、链表节点、空闲对象链、在用数量、容量和分配位图。页头之后按 16 字节对齐放置槽位。管理信息位于申请到的页内，初始化时不依赖另一个动态分配器；空闲对象的首个机器字保存下一空闲对象指针，分配后该空间可由调用者正常使用。

`kmalloc()` 优先使用 partial 链表中的页；没有可用页时，`new_slab()` 向 PMM 申请一页并建立空闲对象链。取出槽位后更新位图和在用数量；页满时从 partial 链表摘除。从满页释放第一个对象时将它重新入链，最后一个在用对象释放后则摘除该 slab 并归还整页。

`kfree()` 将小对象地址按页向下对齐，找到页头，再检查魔数、槽位边界和分配位图。这些断言帮助发现错误调用，但调用约定仍要求有效指针，不保证识别所有悬空指针或任意无效地址。

#### 大对象、地址转换与 Buddy 兼容

大对象的页头占 16 字节，保存魔数和实际页数。先检查 `size + 16` 是否溢出，再计算所需页数并取不小于它的最小二次幂：

```text
needed = ceil((size + 16) / 4096)
npages = 不小于 needed 的最小二次幂
```

例如，8192 字节负载加管理头需要三页，因此实际申请四页。统一向三个后端申请二次幂页数，并把相同的 `npages` 传给 `free_pages()`，可避免 Buddy 的向上取整与对象层释放页数不一致。该策略也能用于 First-Fit 和 Best-Fit，但会增加部分大请求的内部碎片。

`alloc_pages()` 返回 `Page *`，不能直接当作对象地址。实现通过 `page2pa(page) + va_pa_offset` 得到内核虚拟地址，释放时通过 `PADDR()` 和 `pa2page()` 找回描述符，不使用当前工程已注释的 `KADDR`。SLUB 的管理信息不占用 `Page.flags/property/page_link`，这些字段继续由 PMM 管理。

#### 两份提示词与测试设计

第一份提示词要求从零实现两层分配、对象缓存、状态转换、地址转换与 Buddy 页数约定；第二份独立规定不同大小对象、数据隔离、槽位复用、真实内存耗尽及页数守恒的测试。两份完整提示词采用 `[PROMPT]—[RELY]—[GUARANTEE]—[SPECIFICATION]` 结构，见 [SLUB 提示词记录](slub_prompt.md)，也可从团队 [prompt.md](prompt.md) 进入。

## 4.3 分支任务：GDB 调试页表查询过程
**负责人：** 2411276-林靖然

### 4.3.1 调试对象与关键路径

本任务使用带调试信息的 QEMU 4.1.1。宿主机 GDB 附加到 QEMU 进程，查看模拟器的 C 代码；RISC-V GDB 通过 QEMU 的 GDB stub 控制 uCore 的运行。两个 GDB 分别调试模拟器和模拟器中的内核。

以 `kern_init` 的取指为例，QEMU 中观察到的调用路径为：

```text
get_page_addr_code()
    ↓
tlb_fill()
    ↓
riscv_cpu_tlb_fill()
    ↓
get_physical_address()：依据 satp 查询页表
    ↓
tlb_set_page()：写入 QEMU 的软件 TLB
```

TLB 查询位于 QEMU 4.1.1 的 `accel/tcg/cputlb.c`。取指时，`get_page_addr_code()` 查询指令访问对应的 TLB 项；数据读写则分别使用读、写访问的项。在本次写入命中的 `store_helper()` 源码第 1518—1523 行，`tlb_hit()` 先检查普通项；若未命中，再用 `victim_tlb_hit()` 检查备用项；两者都未命中才调用 `tlb_fill()`。调用栈中的 `store_helper → tlb_fill → riscv_cpu_tlb_fill` 说明本次确实走了未命中分支。填充函数调用 `get_physical_address()`；转换成功才执行 `tlb_set_page()`，失败则转入异常处理。这段调用栈只记录了当前写入的一次未命中；QEMU 对其他访存还可能直接通过 TCG 生成的快速代码完成 TLB 查询。

![图 4-1：数据写入经 TLB 未命中进入页表查询](images/05_qemu_store_miss.png)

### 4.3.2 单步观察 Sv39 页表遍历

分页开启后，GDB 读到 `satp=0x8000000000080204`：最高位对应 Sv39 模式，根页表物理地址为 `0x80204000`。本次取指虚拟地址为 `0xffffffffc02000d8`。在 `get_physical_address()` 中单步，得到顶级索引 `0x1ff`，页表项地址 `0x80204000 + 0x1ff × 8 = 0x80204ff8`，读出的页表项为 `0x200000cf`。

![图 4-2：顶级索引、页表项地址与页表项内容](images/02_qemu_sv39_walk.png)

Sv39 的三级索引各占 9 位，每个页表项占 8 字节。`get_physical_address()` 从根页表开始，按当前级索引读出 PTE：无效项导致翻译失败；有效且没有读、写、执行位的项指向下一级；叶子项则要经过权限等检查后才能返回映射。本例读到的 `0x200000cf` 具有有效的 `V/R/W/X` 位，`PPN=0x80000`，所以它是顶级的 1 GiB 叶子项，循环在第一轮结束，不会实际读取下两级页表。

这个叶子项以 `0x80000000` 为物理起点，虚拟地址相对 `0xffffffffc0000000` 的偏移为 `0x2000d8`，故完整物理地址是 `0x80000000 + 0x2000d8 = 0x802000d8`。GDB 中 `get_physical_address()` 返回 0 表示成功；调用者的 `pa=0x80200000` 是按 4 KiB 对齐的物理页基址，加上页内偏移 `0xd8` 得到相同结果。

![图 4-3：取指虚拟地址转换为物理地址](images/03_qemu_fetch_translation.png)

`riscv_cpu_tlb_fill()` 随后调用 `tlb_set_page()`，记录虚拟页 `0xffffffffc0200000` 到物理页 `0x80200000` 的映射。本次填入的软件 TLB 项大小为 4096 字节，`prot=0x7`。

![图 4-4：QEMU 将转换结果写入软件 TLB](images/04_qemu_tlb_fill.png)

为确认这一流程同样作用于数据访存，又追踪了一次 8 字节写入：`MMU_DATA_STORE` 访问 `0xffffffffc0203ff8`。转换成功后，物理页基址为 `0x80203000`，加上页内偏移 `0xff8`，实际物理地址为 `0x80203ff8`。

![图 4-5：数据写入的虚拟地址与物理地址](images/06_qemu_store_translation.png)

### 4.3.3 分页开启前后的比较

重新启动后，在内核物理入口处再次中断。此时 `mmu_idx=1`、`satp=0`，`get_physical_address()` 将 `0x80200000` 转为相同的物理地址：这是 uCore 进入分页前的 Bare 模式访问，无需遍历 Sv39 页表。开启分页后，同一内核的高地址取指则通过上述页表项完成 `0xffffffffc02000d8 → 0x802000d8` 的转换。

![图 4-6：分页开启前的直接地址映射](images/01_qemu_bare_identity.png)

真实 CPU 的 TLB 是硬件中的地址转换缓存；QEMU 的 TLB 是模拟器维护的软件缓存，还服务于来宾地址到宿主机内存访问的加速。Bare 模式下，真实 CPU 无需做 Sv39 页表翻译；QEMU 此时仍进入 `get_physical_address()`，本次观察到的是恒等地址转换。分页后的 PTE 是 1 GiB 叶子项，而本次 `tlb_set_page()` 填入的软件 TLB 项大小为 4 KiB，两者的范围也不必相同。

### 4.3.4 调试细节与 AI 辅助

单步时有两个值得注意的现象：`finish` 显示 `get_physical_address()` 已返回 0，但调用者的赋值语句还未执行，再用一次 `next` 才看到 `ret=0`；Sv39 的循环最多走三级，本次却因顶级项就是叶子项而只读一次 PTE。

建立双重 GDB 会话时，向 AI 询问两种 GDB 各应连接什么目标，以及怎样避开固件阶段的大量访存。根据建议，宿主机 GDB 附加 QEMU，RISC-V GDB 连接 QEMU 的 `localhost:1234`，并按内核地址设置条件断点，最终捕获 `0xffffffffc02000d8` 的取指。遇到 `finish` 后 `ret` 尚未更新时，再询问赋值与返回的执行顺序，并用 `next` 核实。一次误输入 `pi` 进入 GDB 的 Python 解释器，`p/x` 因而报语法错误；退出解释器后改用 `print/x` 继续读取索引和 PTE。

四次运行合计通过 32 组测试，且每次结束时空闲页数与开始时相等。真实耗尽测试分别占住 31927 页和 15703 页，另有一页由保留的 slab 占用，此时确认 `nr_free_pages() == 0`。

构建日志、版本、命令、源文件 SHA-256 和内核镜像 SHA-256 见 [128 MiB 结果](slub_evidence/qemu128M/results.json)、[64 MiB 结果](slub_evidence/qemu64M/results.json)。原 A/B 提交的 Buddy 基线另存于 [基线记录](slub_evidence/baseline/results.json)；新旧内核代码和静态数据占用不同，泄漏判断应比较同一次运行的前后页数。

## 六、实验总结与收获

### 6.1 本实验的重要知识点及其与操作系统原理的联系

| Lab2 中的实现 | 对应的 OS 原理知识点 | 联系与区别 |
|---|---|---|
| `dtb_init()`、`page_init()` 与 `Page[]` | 可用物理内存的发现和登记 | DTB 给出内存范围；内核扣除固件、镜像和页描述符占用后，才登记完整空闲页。课程中的位图和链表都是记录可用空间的方法；本实验用 `Page` 描述每个页框，用空闲链表组织可分配的连续块。 |
| `PADDR()`、`page2pa()` 与 `nbase` | 分页中的页号、页框号和地址转换 | `Page *` 指向管理信息，物理地址指向实际内存，两者不能混用。页号对应地址的高位，页内偏移在翻译时保留；本实验还须处理内核虚拟地址与物理地址之间的固定偏移。 |
| First-Fit、Best-Fit 与 `pmm_manager` | 空闲块查找、碎片和分配策略 | 两种算法共用 `alloc_pages/free_pages` 接口。First-Fit 遇到首个足够大的块就分配；Best-Fit 遍历空闲链表后选最小的可用块。选择策略改变查找工作量和剩余块形状，释放时仍要合并相邻空闲块。 |
| `buddy_fit_pmm_manager` | 伙伴系统与连续内存分配 | 空闲块按 `2^order` 页分类；分配时拆分较大块，回收时用伙伴页号合并。它便于按阶管理大块，但对非 2 的幂页数会向上取整，可能多占页。 |
| `kmalloc()/kfree()` | 页级分配与小对象分配的分层 | 底层分配器以页为单位工作；本实验的 SLUB 从页中切出小对象，较大的请求直接向页分配器申请连续页。空 slab 归还物理页，使对象层的释放最终反映到空闲页计数。 |
| 启动页表、`satp` 与 `sfence.vma` | 多级页表和大页映射 | 内核写入 `satp` 后使用 Sv39。实际调试的顶级 PTE 是 1 GiB 叶子项，因此该地址只查一级；三级是允许的最大深度，并非每次访问都必须走满三级。 |
| QEMU 的 TLB 查询与页表遍历 | TLB 缓存和软硬件协作 | TLB 未命中后才读取页表，成功翻译再填入缓存。实验通过 QEMU 的 C 代码观察这一过程；真实处理器由硬件完成相应工作，内核负责准备页表和设置 `satp`。 |

### 6.2 OS 原理中尚未涉及的知识点

本实验建立了物理页分配和启动地址映射，但没有实现以下机制：

- **按需分页与进程地址空间**：启动页表提供固定映射；没有为不同进程建立独立页表，也没有在缺页时动态补充映射。
- **页面置换和交换空间**：分配器找不到合适的空闲块时返回失败，不会选择已有页面写回磁盘后再分配。
- **内存紧凑**：First-Fit 和 Best-Fit 可合并相邻空闲块，Buddy 可合并空闲伙伴；它们都不会搬迁已占用页面来拼出新的大块。
- **非连续物理页的连续虚拟映射**：`alloc_pages(n)` 申请连续物理页；实验没有把分散的页框重新映射成一段连续虚拟地址的机制。
- **并发分配与跨核 TLB 同步**：当前 SLUB 是单 hart 实现；启动代码中的 `sfence.vma` 也没有扩展为多核之间的同步流程。

### 6.3 实验收获

本实验把“发现内存、管理物理页、分配内核对象”串成了完整流程。DTB 提供的范围不能直接全部分配，必须先扣除固件、内核和页描述符；页分配器解决连续页的组织与回收，SLUB 再处理小于一页的对象，两层通过相同的页接口衔接。

接口匹配不仅要求能调用同名函数，还要明确计量单位和取整规则。`Page *`、物理地址和内核虚拟地址代表不同含义；Buddy 对页数向上取整后，SLUB 必须记录并归还实际页数。验证时也要同时检查对象内容、地址隔离和页数恢复，才能发现仅观察返回值难以发现的问题。

AI 辅助开发需要先明确前置条件、后置条件和错误行为，再用独立测试核实生成结果。SLUB 验证器曾过早结束日志采集，说明验证工具本身也需要检查；补充管理头临界点后，测试才直接覆盖了真正的页数变化边界。QEMU 调试则使页表、地址翻译和 TLB 的关系有了可观察的执行过程。
