## 三、知识梳理

### 问题 1：CPU 复位地址与内核入口

**AI 提问：**

为什么 QEMU 启动后，CPU 的 PC 最初是 `0x1000`，而不是链接脚本指定的 `0x80200000`？内核的 ELF 入口地址和 CPU 复位地址有什么区别？

**我的回答：**

CPU 需要先从复位地址执行，之后跳转到 OpenSBI，由 OpenSBI 完成初始化操作，最后再进入链接脚本指定的内核入口 `0x80200000`。

**学习后的补充：**

CPU 复位地址由当前模拟平台的启动机制决定，而 ELF 入口地址由链接脚本确定。在本实验中，内核镜像已经由 QEMU 提前加载到内存，OpenSBI 负责初始化并将执行权交给内核，而不是此时才加载内核文件。

### 问题 2：为什么需要初始化内核栈？

**AI 提问：**

为什么进入 `kern_init()` 前必须执行 `la sp, bootstacktop`？如果直接执行 `tail kern_init`，可能会出现什么问题？

**我的回答：**

需要先设置栈顶，因为后续函数执行时需要使用栈来存储和操作数据。如果不设置正确的栈指针，数据可能被放到错误的内存位置，导致程序运行异常甚至崩溃。

**学习后的补充：**

刚进入内核时，SP 并不一定完全无效，但它仍然是之前固件执行环境留下的值。uCore 应当使用自己预留的内核栈，而不是继续依赖固件的栈空间。

### 问题 3：`tail` 与 `call` 的区别

**AI 提问：**

`tail kern_init` 完成了什么操作？为什么这里使用 `tail`，而不是普通的 `call kern_init`？

**回答：**

`tail` 用来跳转到初始化函数，不需要像 `call` 一样建立返回地址。因为内核初始化函数不打算返回，如果使用普通调用，后续意外返回可能导致不符合预期的程序行为。

**学习后的补充：**

`tail` 的准确含义是不为本次跳转建立新的返回地址，并不意味着被调用函数一定无法返回。当前 `kern_init()` 本身通过无限循环保证不会正常返回，因此适合使用 `tail`。

### 问题 4：`.bss` 段与内存清零

**AI 提问：**

`.bss` 段主要存放什么数据？为什么需要清零？本次实验中 `edata` 与 `end` 相等，实际清零多少字节？

**回答：**

`.bss` 主要存放没有显式设置初始值的变量。清零是为了避免原有内存中的残留数据影响程序运行，确保这些变量的初始值为零。

本次实验中 `edata` 和 `end` 的地址相同，因此实际清零长度为 0 字节。

**学习后的补充：**

`.bss` 通常用于未显式初始化或者初始化为零的全局变量、静态变量。即使本次构建中清零长度为零，启动代码仍然保留了对应的初始化功能。

### 问题 5：SBI 与 `ecall`

**AI 提问：**

为什么 uCore 不直接使用普通的 `printf()` 输出字符，而要通过 `ecall` 请求 OpenSBI？`a0`、`a7` 和 `mcause=9` 分别表示什么？

**回答：**

uCore 自身没有完整的普通程序运行环境，部分底层操作需要通过 OpenSBI 完成。

其中，`a7` 存放 SBI 服务编号，用来表示需要执行什么操作；`a0` 存放传递的数据；`mcause` 用来记录异常原因，本次 `mcause=9` 表示由 S 模式发起的环境调用。

**学习后的补充：**

本实验没有实现独立的底层控制台驱动，因此借助 OpenSBI 提供的字符输出服务。S 模式并非完全不能访问硬件，而是本实验选择通过 SBI 接口完成输出。

### 问题 6：ELF、BIN 与内核加载

**AI 提问：**

为什么实验中需要生成 ELF 和 BIN 两种文件？它们有什么区别？本次实验究竟由 QEMU 还是 OpenSBI 加载 `ucore.img`？

**回答：**

ELF 可以理解为包含目录和说明信息的文件，除了机器指令，还保存程序结构等信息。BIN 则是去掉这些文件头和索引信息后的原始二进制内容。

本实验由 QEMU 将 `ucore.img` 加载到内存中，而不是由 OpenSBI 读取内核镜像文件。

**学习后的补充：**

ELF 和 BIN 都可能包含机器指令及程序数据。ELF 还可以包含入口地址、符号表和调试信息，因此 GDB 使用 ELF 进行调试。本工程则使用 QEMU 将 BIN 镜像加载到指定地址。
